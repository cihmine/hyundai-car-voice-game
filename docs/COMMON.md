# 공통 개발·빌드·검증 계획
작성: 2026-10-31 · 목표: 2026-11-04 내부 제출

## 1. 이번 개발의 완료 기준
각 앱에서 사용자 핵심 흐름이 실행되고, 종료 후에도 필요한 상태가 복원되며, 서명된 release APK를 깨끗한 테스트 환경에 설치해 시연할 수 있어야 한다. 차량 입력·제어를 모의 처리한 부분에는 지속적으로 '차량 연동 시뮬레이션' 표시를 한다.

공모전 1차는 기획서가 필수이고 개발 산출물은 선택 가산점 대상이다. 그러나 우리 자체 목표는 앱별 소스 코드, 실행 가능한 release APK, 짧은 시연 영상까지 준비하는 것이다. 2차 PT 진출 시에는 실제 동작 가능한 앱이 필요하므로, 모의 차량 연결만으로 2차 기준을 충족한다고 단정하지 않는다.

## 2. 기술 선택과 첫날 확인
다음은 개발 제안이다. 이미 작동하는 프로젝트가 있다면 사용자의 기존 구조를 보존한다.

| 영역 | 기본안 | 첫 작업에서 검증할 것 |
|---|---|---|
| 앱 | Kotlin + Android 네이티브 UI, Compose 우선 | 기존 Android/Automotive 프로젝트·에뮬레이터에서 빌드 및 실행 |
| 플랫폼 | 차량에 직접 설치하는 Android Automotive/Pleos 앱 | 휴대폰 화면 투사형 Android Auto 앱과 혼동하지 않기 |
| 상태 | 순수 Kotlin 상태 전이 + ViewModel + Coroutines | UI와 게임·타이머 로직 분리 |
| 저장 | Room: 기록 / DataStore: 작은 설정 | 실제 선택 버전, 마이그레이션·재실행 복구 |
| 테스트 | 순수 로직 단위 테스트 + 핵심 기기 시연 | 정상 흐름과 위험한 경계 조건 중심 |
| 차량 연결 | 우리가 정의하는 인터페이스 + Mock/Pleos 구현 | 실제 SDK 이름·시그니처·권한·지원 확인 후 연결 |
| 음성 | STT/TTS 인터페이스, Pleos 우선 | 인증·서비스 가용성·한국어 인식·오디오 포커스 |
| 서버 | P0는 서버 없이 실행 | 외부 AI가 필요하면 별도 프록시, 키는 APK 밖 |
| 배포 | 앱별 GitHub 저장소 + release APK | 서명·설치·기능 확인과 커밋 일치 |

공식 시작 가이드는 Android SDK API 34, minSdk 28 이상을 안내한다. compileSdk/targetSdk/AGP/Gradle/JDK/Kotlin/Compose의 실제 조합은 설치된 환경과 공식 샘플의 호환성을 확인해 고정한다. 무조건 최신 버전으로 일괄 올리지 않는다. 필요한 SDK는 Pleos 개발자 계정·사용 신청 및 공식 에뮬레이터로 준비한다.

공식 Maven 주소: https://nexus-playground.pleos.ai/repository/maven-releases/
공식 빠른 시작 예시와 Vehicle 소개의 버전 표기가 다를 수 있다. 소개에 나온 Vehicle 2.3.2를 무조건 사용 가능하다고 가정하지 말고 실제 내려받은 버전과 빌드 결과를 기록한다. 비공개 SDK·바이너리는 재배포 허용 여부를 먼저 확인한다.

### 초기 확인 순서
1. 기존 AGENTS.md, CLAUDE.md, Git 상태, 프로젝트 파일, 설치 도구를 읽는다. 기존 수정사항은 보존한다.
2. Gradle Wrapper를 포함하는 Android 프로젝트를 만들고 빈 화면을 빌드한다.
3. Pleos 에뮬레이터에 설치·실행한다. 사용할 수 없다면 일반 Automotive 환경 테스트와 Pleos 미검증 상태를 분리해 보고한다.
4. 마이크·오디오·SDK 인증·차량 프로퍼티 지원을 작은 확인 화면으로 검증한다.
5. docs/SDK_VERIFICATION.md에 확인한 버전, 권한, 결과, 로그 위치, 미지원 기능을 기록한다.

## 3. 공통 구조
아래 파일·인터페이스 이름은 우리 앱을 위한 설계 예시이며 실제 Pleos SDK 함수명이 아니다.

~~~text
app/                         화면, ViewModel, 앱 시작점
app/src/main/.../domain/      게임 규칙·구역 추정·알람 상태 전이
app/src/main/.../data/        로컬 저장, Repository
app/src/main/.../ports/       차량·음성·시계·AI 인터페이스
app/src/demo/                모의 차량 입력/제어, 고정 시나리오
app/src/pleos/               검증된 SDK 어댑터만 추가
app/src/test/                상태·타이머·중복 처리 테스트
docs/                        PLAN, COMMON, SDK_VERIFICATION, TEST_REPORT
demo/scenarios/              재현 가능한 JSON 입력
demo/STORYBOARD.md           영상 순서·실제/모의 표시
apk/                         제출용 release APK
gradle/wrapper/               재현 가능한 빌드 도구
~~~

- demo와 pleos는 product flavor로 구분하는 방식을 권장한다. SDK를 확보하기 전에는 demo 빌드를 막는 SDK import·의존성을 main에 넣지 않는다.
- demoRelease도 서명된 실제 Android 앱이다. 'release'라는 빌드 종류가 실차 연동 완료를 의미하지는 않는다.
- 실차 연결이 실패했을 때 조용히 가짜 값으로 바꾸지 않는다. '연결 안 됨', '지원 안 됨', '모의 데이터'를 구분한다.
- Clock, VehicleStateProvider, SpeechRecognizer, SpeechSpeaker, EventStore 같은 경계를 둬 실제 연결만 교체할 수 있게 한다.
- 차량 상태는 PARKED / MOVING / UNKNOWN으로 구분한다. 값 없음·오래된 값은 UNKNOWN이며 속도 0만으로 주차라고 판단하지 않는다.
- 미지원 기능은 숨기거나 비활성화 이유를 안내한다. 실패를 성공 화면으로 덮지 않는다.

## 4. 주행 정책과 실행 제약
차량용 앱이라고 모든 기능이 주행 중 허용되는 것은 아니다. 카테고리, 지역 정책, CarUxRestrictions, 실제 차량 상태를 함께 검토한다. 음성 게임의 주행 허용은 확인 전까지 미확정이다. DO 선언으로 정책을 우회하지 않는다.

1번 앱의 '주행 모드'는 우선 모의 상태로 규칙을 검증한다. 플랫폼이 앱 실행을 막는 상황에서는 이를 우회하지 않고 주차 상태의 시연과 설계 설명으로 제시한다. 사용자가 게임 모드를 선택해도 실제 플랫폼 제한을 해제하지 못하게 한다.

2·3번 앱의 핵심 화면은 주차 중 사용한다. 차량 전원 OFF, 프로세스 종료, OS 절전, 강제 중지에서 앱이 계속 실행된다고 가정하지 않는다. 주차 충격 상시 감지와 시동 OFF 상태 기상 알람은 별도 플랫폼·하드웨어 지원이 필요한 검증 과제다.

## 5. 공통 데이터와 신뢰성
- 로그인은 P0에서 제외하고 로컬 사용자 1명으로 시작한다.
- 원본 음성·VIN·상세 위치는 기본 저장하지 않는다. 계정별 학습은 이후 기능이며 P0에서는 기기 내 확인된 명령 별칭 정도만 저장한다.
- 외부 AI·검색을 붙이면 전송 내용을 최소화하고 사용자에게 알린다. 키는 .env나 서버 환경변수로 관리하고 앱 바이너리·Git에 넣지 않는다.
- 네트워크 실패·권한 거부·음성 미인식은 복구 가능한 상태로 처리한다.
- 이벤트 ID와 세션 ID를 사용해 알람, 게임 보상, 충격 알림이 중복되지 않게 한다.
- 음성 명령은 허용된 동작 목록으로 변환하고 검증한다. 모델이 반환한 임의 코드·URL·차량 명령을 실행하지 않는다.
- 앱 삭제/데이터 초기화 시 로컬 기록이 사라진다는 점을 README에 적는다.

## 7. Git 관리와 제출 빌드
앱마다 독립 저장소를 권장한다. 각 저장소만 내려받아도 의존성과 실행법을 알 수 있어야 한다. 다른 비공개 저장소를 자동으로 끌어오게 만들지 않는다.

### 넣을 것
소스, Gradle Wrapper, 버전 고정 설정, 테스트, 모의 시나리오, README, 구현 상태, SDK 확인 기록, APK 또는 Release 링크, 영상 링크, 사용한 데이터·라이선스 설명.

### 넣지 않을 것
서명키·비밀번호·실제 API 키·.env·local.properties·캐시·SDK 비공개 파일·참가자 동의서·전화번호·음성 원본. APK 전체를 ignore하면 제출 파일도 빠지므로 apk/에 복사한 제출용 파일은 별도로 추적한다.

### 권장 커밋 단위
- chore: initialize automotive app and mock environment
- feat: implement core flow
- feat: persist and restore session
- test: cover recovery and duplicate events
- docs: add verification and demo instructions
- release: prepare first-round submission

커밋 횟수 자체에 가산점이 있다고 쓰지 않는다. 작업 경과와 제출 버전을 식별하기 위한 관리 방법이다. 이 문서 작성만으로 GitHub에 업로드된 것은 아니다.

### release 생성 절차
1. 실제 프로젝트에 맞는 Gradle 작업을 확인한다. 아래 이름은 demo flavor 구성 시의 예시다.
2. 필요한 단위 테스트·lint·빌드를 실행한다.
3. 저장소 밖의 전용 keystore로 release를 서명한다. 서명키는 사용자가 별도로 보관한다.
4. APK 서명을 확인하고 새 에뮬레이터에 설치한다. debug APK 이름만 바꾸는 방식은 사용하지 않는다.
5. 핵심 흐름을 수행하고 테스트 보고서에 빌드 커밋·환경·결과를 기록한다.
6. APK를 공식 파일명으로 apk/에 복사하거나 GitHub Release에 첨부한다.
7. Release 노트에 소스 커밋, 빌드 종류, 실제/모의 범위, SHA-256, 알려진 한계를 넣는다.

~~~bash
./gradlew testDemoDebugUnitTest lintDemoDebug assembleDemoRelease
apksigner verify --verbose path/to/app-demo-release.apk
adb install -r path/to/app-demo-release.apk
~~~

위 명령은 프로젝트 생성 후 작업명·도구 경로를 맞춰야 한다. 실행하지 않았는데 성공으로 기록하지 않는다. APK를 별도 커밋하는 경우 APK를 만든 소스 커밋과 최종 제출 커밋을 각각 적는다.

## 8. 최소 검증과 개발 상태 보고
각 앱의 중요한 로직 테스트와 설치·사용 흐름 검증만 수행한다. 구현 내용을 그대로 복사하는 테스트나 의미 없는 화면 테스트를 늘리지 않는다.

docs/TEST_REPORT.md에는 날짜, 환경, 앱/SDK 버전, 소스 커밋, 사례, 기대, 실제 결과, 증빙, 미검증 사유를 남긴다. 'PASS / FAIL / NOT_RUN / BLOCKED'를 구분한다.

docs/IMPLEMENTATION_STATUS.md 예시:

| 기능 | 구현 상태 | 입력 출처 | 검증 환경 | 한계 |
|---|---|---|---|---|
| 실제 타이머 | 미착수 | 앱 시계 | 미실행 | 전원 OFF 보장 없음 |
| 차량 공조 | 설계만 | 모의 예정 | 미실행 | 실차 권한 확인 필요 |

P0 종료 기준: 핵심 흐름 성공, 재시작 복구 성공, 중복 동작 방지 성공, 모의 상태 식별, 키·개인정보 미포함, release 설치 성공, README로 실행 가능. 실제 실차 시험과 정량적 안전·효과 검증은 수행한 경우에만 기재한다.

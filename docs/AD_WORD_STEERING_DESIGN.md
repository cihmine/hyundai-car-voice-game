# 끝말잇기 광고 단어 유도 알고리즘 설계
버전: 0.1 · 작성일: 2026-11-01
대상: 1번 말게임 앱 · Claude Code 구현용 추가 설계
상태: 설계안. 구현·성능 측정·현대자동차 광고 제휴가 완료됐다는 뜻이 아니다.

## 1. 목적과 적용 범위
광고주가 등록한 단어 목록에서 게임에 적합한 목표를 선택하고, AI의 단어 선택을 조절해 AI가 그 단어를 합법적으로 말할 기회를 만든다. 사용자가 '그게 뭐야?'라고 질문하면 광고임을 밝힌 승인 문구를 짧게 읽고 게임으로 복귀한다.

사용자의 답을 강제하거나 예측 답변과 다르다는 이유로 오답 처리하지 않는다. 노출을 보장하는 알고리즘이 아니라 제한된 시간 안에서 자연스러운 노출 가능성을 높이는 알고리즘이다.

기존 01_VOICE_GAME.md는 그대로 두고 이 문서를 추가한다. 기존 오답·재확인·중복 금지·난이도·무효·포인트 규칙은 변경하지 않는다. 이번 모듈은 기존 AI의 '어떤 합법 단어를 말할지'를 결정하는 부분과 설명 요청 흐름에 연결한다. 초성·스무고개 광고는 이번 설계 범위 밖이다.

## 2. 먼저 정할 제품 규칙 — 개발 제안
| 항목 | 초기 제안 |
|---|---|
| 게임 모드 | 일반 모드 / 브랜드 단어 허용 모드 |
| 허용 단어 | 일반 사전 + 게임 시작 시 고정한 승인 브랜드 단어 묶음 |
| 공정성 | 같은 허용 목록을 사람과 AI에 동일 적용 |
| 노출 고지 | 브랜드 모드 안내 및 광고 단어 발화 시 짧은 '브랜드 소개' 표시/음성 |
| 광고 설명 | 사용자가 요청할 때만 승인된 짧은 설명 |
| 노출 빈도 | 한 판 최대 1회, 이전 광고 시작 후 최소 10분 |
| 노출 시작 | 사용자 유효 답변 4회 이후부터 |
| 유도 시도 | 한 에피소드에서 AI 선택 최대 3회, 연결 안 되면 해당 판 유도 종료 |
| 탐색 | 초기에는 AI 현재 차례+다음 차례의 2단계 |
| 사용 중지 | '광고 끄기'로 즉시 유도 중지, 포인트 불이익 없음 |
| 설명 길이 | 기본 1~2문장, 추가 설명은 별도 요청 |
| 주행 | 실제 플랫폼 정책을 따름. 시제품 시연은 주차 상태 중심 |
| 금전/보상 | 광고 설명 청취·클릭·관심 여부로 게임 보상을 바꾸지 않음 |

숫자는 제품 기본안이며 측정 후 조정한다. 모드·고지는 명확히 제공하되 설명을 듣도록 강요하지 않는다. 광고를 꺼도 이미 시작한 판의 허용 단어 목록을 바꾸지 않아 판정이 흔들리지 않게 한다. 다음 판부터 일반 모드를 선택할 수 있다.

실제 운영의 표시 문구·광고 약관·개인정보 처리는 출시 시 별도 검토한다. 이 문서가 법적 검토 완료를 의미하지는 않는다.

## 3. 광고 단어 선정: 등록 → 검증 → 게임 적합성
### 3.1 광고주가 제공할 내용
- 단어의 정식 표기와 승인된 읽는 법.
- 브랜드/차종/서비스 등 분류.
- 검증된 짧은 소개, 추가 소개, 자료 출처·확인 날짜.
- 캠페인 시작/종료 시각과 콘텐츠 버전.
- 실제 제휴인지 시연용 브랜드 소개인지 구분하는 표기.

단어와 광고 설명은 별개다. 새 차종명을 사전에 넣었다는 이유로 가격·출시일·성능을 AI가 생성하게 하지 않는다.

### 3.2 규칙 적합성
1. 정확한 정식 명칭과 게임용 음절 표기를 확정한다.
2. 숫자·영문·공백이 있으면 읽기와 연결 규칙을 명시적으로 정한다. 임의로 '아이오닉 5'를 '아이오닉'으로 줄여 같은 단어라고 취급하지 않는다.
3. 같은 단어의 별칭·표기 변형은 canonicalId 하나로 중복을 검사한다.
4. 두음법칙은 기존 RuleEngine의 허용 연결 함수를 공통 사용한다. 광고 전용 예외를 만들지 않는다.
5. 광고 단어를 낸 뒤 사용자가 답할 수 있는 미사용 단어가 있는지 현재 상태에서 다시 검사한다.

### 3.3 광고 적합성 지표
등록 시 전체 사전 기준으로 계산하고, 실행 때 사용 단어와 난이도를 반영해 재계산한다.

| 지표 | 의미 | 용도 |
|---|---|---|
| inboundWords | 광고 단어의 첫 음절로 이어지는 일반 단어 수 | 진입 경로 후보 |
| inboundResponseMass | 현재 게임에서 그 진입 단어를 사용자가 말할 추정 비중 | 실제 유도 가능성 |
| outboundWords | 광고 단어 뒤에 가능한 일반 단어 수 | 게임 지속 여부 |
| familiarOutbound | 그중 쉬운 단어 수 | 의도치 않은 한방 공격 방지 |
| recognitionRisk | 읽기·표기 혼동 가능성 | 음성 게임 적합성 |
| contentReadiness | 소개 문구 검수·유효기간 상태 | 노출 가능 여부 |

초기 강제 조건: 현재 상태에서 익숙한 후속 일반 단어 3개 이상이 있는 광고 단어만 자동 노출한다. '3개'는 검증 전 제안값이다. 익숙함은 사전의 편집된 난이도 태그로 시작한다.

등록할 수 없는 차종명도 있을 수 있다. 진입·후속 연결이 부적합하면 자동 유도 목록에서 빼고, 사용자가 별도로 요청한 브랜드 정보나 주차 메뉴에서 소개한다. 게임 규칙을 바꿔 억지로 넣지 않는다.

### 3.4 연결 예시
'현대'를 브랜드 허용 목록에 넣었다고 가정한 알고리즘 예시:

- 현재 AI가 '상'으로 시작해야 한다.
- AI가 '상표'를 선택한다.
- 사용자가 '표현'이라고 답하면 AI가 '현대'를 낼 수 있다.
- '현대' 뒤에는 '대나무', '대문', '대장' 같은 후속 후보를 검토한다.

다른 응답:
- 사용자 '표정' → 다음 AI 시작은 '정', 광고를 강제로 넣지 않는다.
- 사용자 '표범' → 다음 AI 시작은 '범', 다른 목표 또는 일반 진행.
- 사용자 '표현'이 이미 쓰인 단어라면 해당 경로를 기대값에서 제거한다.

이 예시는 연결 구조 설명용이며 실제 현대자동차 캠페인이나 신차 소개가 아니다. 예시 일반 단어도 구현에 사용하는 사전 정책으로 검수한다. 광고주가 원하는 차종명이 이 예시처럼 잘 이어진다고 가정하지 않는다.

## 4. 구조: 규칙·플레이 품질·광고 계획을 분리
| 모듈 | 책임 |
|---|---|
| RuleEngine | 유효 단어, 음절 연결, 중복·별칭, 두음법칙 |
| NormalWordPolicy | 기존 난이도에 맞는 AI 후보·게임 품질 점수 |
| CampaignCatalog | 유효한 광고 단어와 승인 설명 |
| ResponseModel | 현재 차례에서 사용자가 답할 단어의 추정 분포 |
| AdPlanner | 광고 도달 가능성과 일반 진행 품질을 비교 |
| AdEligibilityPolicy | 모드·빈도·기간·재생 상태 등 노출 조건 |
| ExplanationController | '그게 뭐야?' 의도·타이머·설명·복귀 |
| AdEventStore | 중복 없는 발화/설명 기록과 빈도 제한 |

AdPlanner는 RuleEngine의 판정을 수정할 수 없다. LLM이 없거나 네트워크가 끊겨도 로컬 카탈로그와 승인 문구로 시연할 수 있다. 실제 AI 모델은 낯선 설명 요청의 의도 분류나 승인 정보에 근거한 후속 질문 답변을 보조하는 정도로 제한한다.

## 5. 데이터 설계
### 5.1 게임 사전
WordEntry:
- canonicalId, writtenForm, spokenForm
- firstSyllable, lastSyllable
- aliases, partOfSpeech, category
- familiarity: 0~1 편집 점수, difficultyTags
- isBrandWord, dictionaryVersion

정규화는 오탈자·유사 발음까지 무조건 정답 처리하는 방식이 아니다. 애매한 STT는 사용자 재확인을 거친다. 별칭은 승인된 목록만 쓴다.

### 5.2 캠페인
CampaignEntry:
- campaignId, version, status: DRAFT/APPROVED/PAUSED/EXPIRED
- wordId: WordEntry 참조
- contentKind: DEMO_BRAND/PAID_SPONSOR
- disclosureText
- shortExplanation, longExplanation, approvedFactIds
- evidenceUrl, verifiedAt, validFrom, validUntil
- priorityWeight: 동일 품질 후보 간 우선순위용, 초기값 1
- limits: perRoundCap, minIntervalSeconds
- compatibleRuleVersions

동일 wordId가 여러 캠페인에 속하면 하나를 선택하고, 발화 한 번을 여러 광고 노출로 중복 기록하지 않는다. 캠페인 업데이트가 기존 판의 단어 사전을 바꾸지 않게 한다. 중지·만료 상태는 실행 직전에 다시 확인한다.

### 5.3 계획 상태
PlannerContext:
- sessionId, roundId, turnId, stateVersion
- playerToMove, requiredHeads, usedCanonicalIds
- ruleVersion, dictionaryVersion, campaignVersion
- difficulty, validUserTurnCount
- adEnabled, adShownThisRound, lastAdStartedAt
- steeringEpisodeId, remainingPlanningDecisions

Decision:
- chosenWordId, reason: NORMAL/DIRECT_AD/STEERING
- targetCampaignId(nullable)
- estimatedReach, modelKind, horizon
- gameplayScore, coverageMass, elapsedMs
- evaluatedStateVersion

Decision은 개발용 진단 정보다. 사용자가 단어를 거절했거나 설명하지 않았다는 이유로 게임 결과를 바꾸지 않는다.

## 6. 알고리즘 1: 후보를 만들고 광고 기회를 찾기
### 6.1 공통 전처리
1. 정상 게임 엔진이 유효하다고 판단하는 모든 현재 AI 후보를 얻는다.
2. 난이도에 맞는 기본 점수 G(a)를 0~1로 계산한다. 광고 모듈을 껐을 때의 후보 선택과 동일한 기준을 사용한다.
3. 최상위 기본 점수와 차이가 0.10 이내인 후보만 광고 계획에 사용한다. 임계값은 개발 제안이다.
4. 광고 단어 자체도 합법성과 품질 조건을 통과해야 한다.
5. 광고 조건이 꺼졌거나, 제한에 걸렸거나, 유효 캠페인이 없으면 NormalWordPolicy로 복귀한다.

후보 품질 점수에는 익숙함, 현재 난이도 적합성, 후속 답변 가능성을 넣는다. 모든 광고 목표를 위해 희귀·막힘 단어를 고르는 선택은 제거한다.

### 6.2 바로 말할 수 있는 경우
광고 단어가 현재 후보에 있고 허용 목록·미사용·계속 진행 조건·광고 조건을 모두 만족하면 직접 노출 후보가 된다. 반드시 광고를 고르는 것은 아니며 아래 게임 품질 제한과 종합 점수를 적용한다.

### 6.3 한 차례 유도: 시제품의 기본
현재 AI 후보 a를 말한 뒤 사용자가 낼 수 있는 합법 단어 집합 U(s,a)를 구한다.

광고 단어 t를 다음 AI 차례에 말할 가능성의 추정치:
P(t | s,a) = 합계 [사용자 답 u의 추정 확률 × 다음 상태에서 t가 합법적으로 노출 가능한지(0 또는 1)]

중요한 순서:
- AI 후보 a를 사용 목록에 추가한다.
- 사용자 답 u를 사용 목록에 추가한다.
- 그다음 t의 합법성과 후속 답변 가능성을 검사한다.

마지막 음절만 맞는다고 성공으로 세지 않는다. 이미 쓴 단어, 브랜드 모드, 캠페인 만료, 노출 제한, 후속 단어 부족을 모두 반영한다.

### 6.4 여러 목표를 동시에 평가
광고 단어마다 별도로 계산한 확률을 그대로 더하면 한 사용자 답변이 여러 목표로 이어질 때 중복 계산된다.

다음 AI 차례에 하나라도 광고를 말할 수 있는지:
P(any eligible ad | s,a) = 합계 [p(u | s,a) × I(다음 상태에 적격 광고 후보가 1개 이상)]

그 상태에서 어떤 광고를 선택할지는 게임 품질, 노출 여부, 캠페인 우선순위로 정한다. 여러 가능한 광고가 있다고 성공 확률이 100%를 넘으면 구현 오류다.

## 7. 알고리즘 2: 짧은 확률 탐색
P0 이후 필요하면 현재 AI 차례를 포함한 최대 H개 AI 차례를 탐색한다. H=2는 '현재 AI→사용자→다음 AI'까지다. 사용자 답변은 선택권이 없으므로 최댓값이 아니라 확률 가중 평균으로 평가한다.

V(s,h): 상태 s에서 남은 AI 차례 h번 안에 허용 광고가 등장할 추정 확률.
- h=0, 게임 종료, 사용자가 광고 중지, 유효 목표 없음이면 0.
- 적격 AI 후보 a가 광고 단어이면 Q(s,a,h)=1.
- 일반 단어 a이면:
  Q(s,a,h) = Σ[u∈U(s,a)] p(u | s,a) × V(next(s,a,u),h-1).
- V(s,h)는 품질 조건을 통과한 AI 선택의 Q 중 최댓값.
- 실제 발화 선택에는 8절의 일반 게임 품질 점수도 적용한다.

이 V는 목표 도달을 우선하는 탐색 정책의 모델 추정치다. 실제 혼합 선택 정책의 성공률과 같지 않을 수 있다. 측정 전 실사용 성공률로 표시하지 않는다.

BFS로 단어 길만 찾으면 AI가 사용자 차례까지 선택할 수 있다고 가정하는 오류가 생긴다. 탐색 상태는 차례, 사용 단어, 난이도, 허용 목록을 포함해야 한다. 각 탐색 분기는 사용 단어 집합의 별도 상태를 유지한다.

### 계산량 제한
초기 구현은 H=2로 충분하다. 기본안을 다음처럼 둔다.
- AI 후보 최대 12개: 정상 후보와 적격 광고 후보를 포함.
- 예상 사용자 답 상위 20개.
- 계획 계산 시간 예산 100ms. 앱 전체 STT/TTS 지연 목표와는 다른 값이다.
- 일반 답변은 먼저 계산해 두고, 시간 초과 시 즉시 일반 답을 사용한다.
- 후보 축소와 시간 예산은 개발 값이며 기기별로 측정 후 조정한다.

상위 20개만 남길 때 그 확률을 다시 합계 1로 만들지 않는다. 나머지 확률은 OTHER로 유지하고 도달 기여 0으로 둔다. 그러면 선택한 응답 모델·탐색 범위 안에서 보수적인 도달 추정이 된다. 예: 포함된 응답의 확률 합이 0.7이면 coverageMass=0.7로 기록한다. 실제 인간 행동에 대해 수학적 하한을 보장한다는 뜻은 아니다.

## 8. 사용자 응답 모델과 최종 선택
### 8.1 처음에는 학습 없이 시작
상황에 합법적인 일반 단어 u의 가중치를 편집된 익숙함·난이도 태그로 만든다.
p0(u | s,a) = weight(u) / 모든 합법 사용자 답의 weight 합.

이 확률은 초기 가정이다. 한국인이 해당 단어를 실제로 말할 확률을 측정했다고 표현하지 않는다. 광고 단어를 사용자가 말하는 경우도 허용 목록에 있으면 사용자 후보에 포함한다. 사용자가 목표 단어를 먼저 말하면 해당 단어는 사용됨 처리하고 AI 광고 기회로 세지 않는다.

### 8.2 추후 빈도 보정
원본 음성을 수집하지 않고, 확인된 정답의 단어 ID와 제한된 문맥(필요 음절·난이도·사전 버전)을 집계할 수 있다.
p(u | c) = [count(u,c) + α × p0(u | c)] / [N(c) + α]

현재 상태에서 불법이 된 단어는 제거하고 전체 합을 다시 정규화한다. 이 정규화는 합법 후보를 정하는 단계이며, 이후 상위 20개를 잘라낼 때는 재정규화하지 않는다.

α는 과거 빈도보다 초기 가정을 얼마나 유지할지 정하는 조절값이다. 초기 예시는 20이지만 실험값이다. 데이터가 없으면 p0만 사용한다. VIN·위치·민감 정보는 이 기능에 필요하지 않다. 서버 집계는 사용자 안내와 필요한 처리 조건을 갖춘 이후 단계다.

### 8.3 최종 점수
합법성·품질·빈도 제한을 통과한 후보에만 적용한다.
Score(a) = 0.7 × G(a) + 0.3 × Q(s,a,H)

가중치는 초기 제안이다. 상위 점수 후보 중 일정 범위에서 가중 추첨해 늘 같은 단어를 말하지 않게 할 수 있다. 테스트는 시드를 고정한다. 광고 예산이나 우선순위가 합법성·플레이 품질의 강제 조건을 넘게 해서는 안 된다.

선택한 일반 단어의 목표 도달 가능성이 너무 낮으면 광고 유도를 포기한다. 초기 임계값 0.15는 '기대값 모델상 가능성'의 제안이며 보장 확률이 아니다. 같은 상태의 일반 정책 대비 개선이 없으면 굳이 유도하지 않는다.

## 9. 경로 재계산과 실행 직전 검증
- 사용자 답이 확정될 때마다 현재 상태에서 다시 계획한다.
- 예상과 다른 답도 합법이면 그대로 인정한다.
- 목표 단어가 이미 쓰였으면 다른 목표를 고르거나 일반 진행한다.
- 3번의 AI 결정으로도 연결되지 않으면 해당 판 광고 유도 에피소드를 끝낸다. 대기·오인식 재확인은 새 결정으로 세지 않는다.
- 이전 계획은 미래 행동 스크립트가 아니다. 다음 차례에서 그대로 실행하지 않는다.

비동기 계획 완료 시 evaluatedStateVersion이 현재 상태와 다르면 버린다. TTS 직전에도 단어 미사용 여부, 캠페인 상태, 사용자 광고 설정, 노출 제한을 검사한다. 최신 조건이 바뀌었으면 준비된 일반 답을 재검증 후 사용한다.

캐시를 쓴다면 requiredHeads만을 키로 삼지 않는다. usedIds의 해시, 차례, 규칙/사전/캠페인 버전, 난이도, 남은 노출 예산과 탐색 깊이를 포함한다. 초기 구현은 캐시 없이 정확성을 먼저 확보한다.

## 10. 설명 요청과 게임 복귀
### 10.1 노출과 소개를 구분
- AI가 광고 단어를 말할 때 짧은 브랜드 고지와 단어를 재생한다. 고지 문구는 게임 단어로 파싱하지 않는다.
- 사용자가 관심을 묻지 않으면 광고 설명을 자동 재생하지 않는다.
- '그게 뭐야?', '무슨 차야?', '뜻 알려줘'는 직전 단어 설명 의도로 처리한다.
- 일반 단어에 대한 질문은 사전 설명이다. 직전 단어와 무관한 광고로 연결하지 않는다.
- 실제 제휴가 없는 시제품은 '브랜드 소개 데모'로 고지한다.

### 10.2 타이머
설명 요청 감지 → 주차 타이머 잔여값 저장·중지 → 설명 → 같은 차례·같은 잔여값 복귀.
설명을 듣는 동안 패배시키지 않고, 매번 새 10초를 지급하는 방식으로 바꾸지도 않는다. 주행 규칙에서는 원래 답변 제한시간이 없다.

음성 인식이 늦더라도 설명 요청 발화 시작 시점을 이용해 타임아웃과 경합을 해결한다. 사용자 발화 중에는 기존 게임의 인식 대기 규칙을 따른다.

### 10.3 설명 문구
템플릿:
'[광고/브랜드 소개 데모] [정확한 차종명]은 [승인된 한두 가지 특징]을 가진 차량이에요. [마지막 음절]로 이어 주세요.'

광고 고지는 상황에 맞게 자연스럽게 읽되 누락하지 않는다. 출처 없는 '최고', '가장 안전', 가격·출시일을 생성하지 않는다. 기간 만료 후 '새로 출시' 같은 시점 표현을 계속 재생하지 않는다.

설명 도중 '그만'은 기존 게임 종료 규칙과 충돌할 수 있으므로 기존 명령 문맥으로 판단한다. '설명 그만'은 설명만 중지, '게임 그만'은 무효 종료, 불분명하면 확인한다. 알림·통화로 중단되면 오디오 포커스 규칙을 따른다.

## 11. 이벤트·빈도 제한·통계
이벤트 예:
- AD_RESERVED: 발화 직전 제한 슬롯 확보.
- AD_STARTED: 브랜드 고지/단어 재생 시작.
- AD_WORD_COMPLETED: 광고 단어 재생 완료.
- AD_EXPLANATION_REQUESTED: 사용자가 설명 요청.
- AD_EXPLANATION_COMPLETED: 승인 소개 재생 완료.
- AD_INTERRUPTED: 재생 중단.
- AD_DISABLED: 사용자 중지.
- PLANNER_FALLBACK: 이유와 일반 진행.

중복 키: roundId + aiTurnId + campaignId + eventType. 중단·재시작·콜백 재전송에서 중복 집계하지 않는다. 한 번 중단된 광고를 반복해 재생하지 않도록 빈도 제한은 AD_STARTED부터 소비한다. AD_RESERVED만 있고 시작되지 않은 경우 정리하되 진행 중 재생 여부를 먼저 확인한다.

사용자가 말한 광고 단어는 AI 노출로 집계하지 않는다. 승인된 설명을 실제로 들은 경우 별도 설명 이벤트를 남길 수 있으나, 단어 노출 수와 혼합하지 않는다.

시제품은 로컬 통계만 만든다. 실제 광고 과금·매출 보고 체계는 후속 설계다. 게임이 무효로 끝나도 이미 들려준 광고 기록은 사실대로 보존하고 게임 포인트는 별도로 무효 처리한다.

## 12. 구현용 의사코드
실제 SDK API가 아닌 앱 내부 설계이다.

~~~text
chooseAiWord(state):
    baseline = normalPolicy.choose(state)
    if !adsAllowed(state): return normal(baseline)

    allowed = ruleEngine.legalAiWords(state)
    candidates = nearNormalQuality(allowed, epsilon=0.10)
    campaigns = catalog.eligible(state)

    if campaigns.empty or candidates.empty:
        return normal(baseline)

    best = normal(baseline)
    for action in boundedCandidates(candidates, includeEligibleAds=true):
        if deadlineReached(): return normal(baseline)
        q, coverage = reachWithinAiTurns(state, action, campaigns, H=2)
        score = 0.7 * gameplayQuality(action) + 0.3 * q
        best = compare(best, action, score, q, coverage)

    if best.isSteering and best.reach < 0.15:
        return normal(baseline)
    if !freshlyValid(best, currentState):
        return normal(normalPolicy.choose(currentState))
    return best

reachWithinAiTurns(state, action, campaigns, h):
    if h <= 0: return 0
    if !legal(action, state): return 0
    afterAi = applyAiWord(state, action)
    if eligibleAdAction(action, state, afterAi):
        return 1
    if h == 1: return 0

    distribution = responseModel.fullLegalDistribution(afterAi)
    selected, otherMass = takeTopWithoutRenormalizing(distribution, 20)
    q = 0
    for (userWord, probability) in selected:
        next = applyUserWord(afterAi, userWord)
        q += probability * bestQualityConstrainedReach(next, h - 1)
    return q  // OTHER contribution is 0; keep coverage separately
~~~

보충: baseline에도 같은 척도의 점수를 계산해 비교한다. 의사코드에서 reachWithinAiTurns의 수치와 함께 coverageMass를 반환하는 결과 객체를 구현한다. helper들을 정의하지 않은 채 정상 동작한다고 주장하지 않는다. 광고 후보가 현재 단어 제한을 통과하지 못하면 includeEligibleAds가 강제로 삽입해서는 안 된다. 모든 상태 분기는 별도의 불변 상태로 평가한다.

## 15. 평가 방법
처음에는 사람이 말할 확률을 모른다. 고정된 단어 선택 시뮬레이터로 구현 오류를 찾고, 이후 소규모 실제 플레이로 응답 모델을 보정한다.

같은 단어 목록·난이도·시작 상태·사용자 응답 정책·난수 시드를 사용해 일반 선택과 유도 선택을 비교한다. 입력 상태가 달라지면 같은 고정 답을 강제로 먹이지 말고 각 상태의 합법 답변을 같은 사용자 정책으로 생성한다. 광고 ON/OFF 비교 모두 같은 브랜드 허용 사전을 써야 차이를 분리할 수 있다.

지표:
- 적격 판 대비 광고 단어 발화 완료 비율.
- 유도 시도 대비 발화 성공 비율.
- 설명 요청 비율: 설명 요청 수 / 광고 단어 발화 완료 수.
- 유도 중 희귀 단어 선택·후속 후보 부족·게임 중단 비율.
- 일반 정책 대비 플레이 품질 점수 변화.
- 계획 지연 p50/p95, 예산 초과 비율.
- 예측 확률과 실제 도달 빈도의 차이.

수치 목표는 실험 후 정한다. 표본 수, 모델 종류, 모의/사람 플레이 여부를 함께 기록한다. 시뮬레이터에서 성공한 비율을 실제 사용자의 광고 효과나 매출로 환산하지 않는다.

## 16. 시연과 기획서 연결
시연은 두 가지를 함께 보여준다.
1. 연결 성공: 일반 단어 선택 → 사용자의 자발적 연결 답 → 브랜드 단어 → 질문 → 짧은 승인 소개 → 정상 복귀.
2. 연결 실패: 예상 밖 답 → 합법 답 인정 → 일반 게임 계속.

개발자 패널에는 목표 후보·추정 도달 가능성·현재 선택 이유를 표시할 수 있다. 주차 상태 개발 시연용 패널이며 실제 게임 화면에서는 복잡한 정보를 보여주지 않는다.

기획서용 한 문장:
'게임의 단어 연결 구조와 예상 응답을 활용해 브랜드 단어가 자연스럽게 등장할 기회를 만들고, 사용자가 설명을 요청할 때 승인된 정보를 제공하는 음성 광고 모델.'

시제품은 '브랜드 소개 데모'로 제시한다. 실제 광고 계약, 차종 출시 정보, 주행 중 사용 승인, 광고 효과 검증을 확보한 것처럼 표현하지 않는다.
